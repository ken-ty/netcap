# 設計

## コマンドの骨格は tailscale から借りた

- **`get` (設定) と `status` (実物) を別コマンドに割る。** 「再起動したらどうなるか」と
  「いまどうなっているか」は別の問いなので、1 表に混ぜない。`on` / `off` / `set` / `use` の
  あとも実物を読み直して表にする
- **`set` は永続する設定だけを変える。** いま絞っている最中なら、その値で張り直す
- **`on` の flag は「今回の完全な希望状態」。** `--up` と `--down` は両方セットで指定する。
  片方だけはエラーにして、「上りだけ絞ったつもりで下りが既定のまま」を構造で防ぐ

動詞だけは借りていない。帯域の「上り/下り」で up/down を既に使っているので、`on` / `off` にした。
プロファイルは tailscale に無い概念で、複数台をまとめて扱うために足した。

## 素通しにする宛先

絞るのはインターネット宛ての通信だけで、次の宛先は shaper を通さない。インターネットに出ない
通信を絞る理由は無い。

| 宛先 | 範囲 |
| --- | --- |
| プライベート IP (同じ LAN) | 10/8、172.16/12、192.168/16 |
| CGNAT 帯 (Tailscale などの VPN が使う) | 100.64/10 |
| ループバック、リンクローカル、マルチキャスト | 127/8、169.254/16、224/4 |

これとは別に、インターネット宛てでも **ICMP と DNS (53)** は絞らない。回線の遅延を ping で
監視しているとき、shaper の待ち行列を測ってしまわないため。Windows は DNS だけを明示的に
除外していて、ICMP が絞られないことは確かめていない。

100.64/10 を素通しにしても、VPN の通信がまるごと絞られないわけではない。素通しになるのはトンネルの
内側のパケットで、インターネット越しの相手へ出る外側の暗号化された UDP は、相手のグローバル IP
宛てなので絞られる。内側と外側で二重に数えないための除外。

## root で動くものの置き場所

NOPASSWD で root になれる本体は、**置き場所の親ディレクトリまで root だけが書ける**ことが前提。
利用者が書けるディレクトリにあると、ファイル自体が root 所有でも差し替えられ、`sudo -n` で
パスワード無しに root が取れる。Homebrew を使ってきた Mac では `/usr/local/sbin` や
`/usr/local/etc` が利用者の持ち物になっていることがある。

だから本体は `/Library/PrivilegedHelperTools`、設定は `/etc` に置き、`install.sh` が親ディレクトリを
`/` まで辿って所有者と書き込み権限を検査する。設定は source せず、数値の key=value として読む。

Windows の `C:\ProgramData` は既定で Users が配下に書き込めるので、`install.ps1` が継承を切り、
SYSTEM と Administrators だけが書けるようにする。

## pf と dnctl は自分の分だけ触る

- pf のルールはアンカー `com.apple/netcap-netshape` に読み込み、main ruleset (`/etc/pf.conf`) は
  差し替えない。macOS の既定の `/etc/pf.conf` にある `dummynet-anchor "com.apple/*"` が
  アンカーを評価する。受け口が無ければ、差し替えずに止まる
- `off` はアンカーを空にし、pipe 1 / 2 だけ消す。`dnctl flush` はしない
- pf の有効化は参照カウント (`pfctl -E` の token) で、`off` は自分の token だけ返す

dnctl の pipe 番号は機械全体で 1 つの空間なので、Network Link Conditioner など pipe 1 / 2 を使う
道具とは同時に使えない。

## macOS の dnctl は pipe 2 の帯域を表示できない

`dnctl list` は 2 本目以降の pipe の見出し行を出さない (`dnctl pipe 2 show` は空、`dnctl -s list`
は segfault。macOS 26 で確認)。だから status の下りは、pipe が 2 本あることを dnctl で確かめた
うえで、値だけ `on` 時の記録 (`/var/run/netcap-netshape.applied`) から読み、表では `*` を付ける。
値が実際に効いていることは下の実測で確かめた。

## Windows のポリシーは永続の保存先に置く

再起動で消える ActiveStore のほうが mac の `--boot off` に近いが、ActiveStore は宛先の条件
(`-IPDstPrefixMatchCondition`) を保持せず、宅内宛ても絞ってしまう (実測で宅内への送信が
20.8 → 1.8 Mbit/s)。永続の保存先では宅内は 20.6 Mbit/s のまま、WAN の上りだけ 2 Mbit/s 以下に
なった。そのため Windows では再起動しても状態が残る。

## 実測

macOS の端末 1 台で、`scripts/measure.sh` を使って測った (2026-09-21、4G 相当の回線)。各行は
1 回の転送で、curl の下り・上り (Mbit/s) と、その最中の 1.1.1.1 への ping (ICMP は shaper を通らない)。

| 条件 | 下り | 上り | ping 中央値 / p95 / max (ms) |
| --- | ---: | ---: | --- |
| off ×3 | 18.5〜32.8 | 5.2〜8.0 | 38〜46 / 60〜315 / 255〜477 |
| **on 1/1 ×3** | **0.52〜0.72** | **0.35〜0.85** | 32〜37 / 48〜184 / 77〜260 |
| off ×1 | 30.5 | 5.4 | 51 / 311 / 317 |
| off ×1 | 24.7 | 7.3 | 35 / 80 / 406 |
| **set 2/3 ×2** | **2.04〜2.65** | **0.90〜1.33** | 38 / 116〜148 / 223〜298 |
| off ×1 | 32.0 | 6.9 | 40 / 175 / 215 |

- curl は上限に張り付く。2/3 で下り 2.0〜2.7 と上りより高いので、上下が別々の pipe で効いている。
  上限未満に収まるのは、その端末自身の他の通信が同じ pipe を分け合うため
- 1/1 のとき ping の p95 は 3 本中 2 本で 50ms 前後に収まった (off は 60〜315)。ただし off の
  ping は転送が数秒で終わるためサンプルが 9〜10 個しかなく、「遅延が跳ねない」とまでは言えない

## 成り立ち

作者が FWA (5G のホームルーター) の回線で League of Legends を遊んでいると、同じ回線の別の
端末のダウンロードで何度もゲームの遅延が跳ねた。ルーターには QoS が無いので、端末の側で絞る
ことにしたのが始まり。

別の日 (2026-09-20) に、回線を分け合う別の Mac を上下 1 Mbit/s に絞る A/B を取ると、ゲーム側
から見た WAN 遅延は 500〜1,600ms から中央値 44ms に戻った。
